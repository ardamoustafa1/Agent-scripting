# ADR-0014: Audit v2 — immutable hash-chained trail, checkpoints, WORM archive, SIEM, audit worker

- **Status:** Accepted · 2026-10-01
- **Amends:** [ADR-0011](0011-api-foundation.md) (audit table shape, advisory-lock chaining), CLAUDE.md §4 "IDs are UUIDv7" (audit events use ULID — see below)
- **Related:** [SECURITY §7](../SECURITY.md), [DOMAIN AuditEvent](../DOMAIN.md), CLAUDE.md §6, [PROGRESS](../PROGRESS.md) step 6

## Context
Prompt 6 asks for an audit module that passes an external audit: a richer event (actor types user/system/apiClient/connector, reason, JSON Patch or before/after with PII masked, interactionId, metadata), ULID ids, DB-enforced immutability, a per-tenant hash chain with signed checkpoints and optional S3 Object Lock, automatic collection (mutations, domain events, auth, sensitive reads), monthly partitions with retention and archiving, a query/export/verify API, SIEM delivery with guarantees, a separate session-event stream with the same integrity, and tests for tampering, unauthorized deletion and ≥ 10k events/s.

## Decision

### Event and hash
- `audit_events` columns: id (ULID), tenant_id, seq (gap-free per tenant), hash_version, action (`namespace.verb` or `domain.entity.verb`), actor_type/actor_id + `actor` JSONB (displayName, ip, userAgent, sessionId), resource (`target_*` columns, API name `resource`), outcome, reason, diff, correlation_id, interaction_id, metadata, occurred_at (business time), recorded_at (chain time), prev_hash, hash, generated `search` tsvector.
- `hash = SHA-256(prevHash + canonicalJSON(event))` over **every** persisted field (v2 input: `hashInputV2`; the whole `actor` details object, so injected keys are detected). Prompt-3 rows keep `hash_version = 1` and their original algorithm.
- Values are sanitized before hashing (NUL → U+FFFD, -0 → 0, bigint → string) so a JSONB round trip recomputes the same hash. Size caps per field (1 KiB text, 256 KiB JSON).
- Diffs: `snapshot` (changed keys only) or RFC 6902 `patch`; sensitive keys (`@pii`/`@secret`/`@pci` list + per-call classified variable names) are masked at any depth — the change stays visible, the value never.
- **ULID vs UUIDv7:** the request specifies ULID. Both are 128-bit and time-ordered; ULIDs are generated by a monotonic, injectable factory (`common/ids/ulid.ts`). Other entities stay UUIDv7.

### Write path
- Same transaction as the change (CLAUDE.md §6). Per tenant, `audit_chain_heads` is locked `FOR UPDATE` (replaces the advisory lock + max(seq) scan); a batch takes the lock once and inserts all rows with one `INSERT … SELECT FROM unnest(…)`. recorded_at is clamped to be monotonic per tenant, so seq order equals partition order. The head row is a cache: verification never trusts it.
- Throughput: per-tenant appends are serialized by design (a chain is a total order). The 10k events/s gate is measured on the real writer, batched (500/tx), 8 tenants in parallel, as `verbis_app`, with full verification afterwards (`test/perf`). Single-row request audits are bounded by the request transaction; the lock is held only from the audit insert to commit.

### Immutability
- No UPDATE/DELETE/TRUNCATE grants for `verbis_app` or `verbis_audit_worker`; BEFORE UPDATE/DELETE row triggers (inherited by every partition) and TRUNCATE triggers on parents and each partition block even the owner. Partitions have no grants and RLS enabled (direct access denied). The only removal path is `audit_drop_partition` (below).
- Checkpoints, archive registry: append-only the same way.

### Checkpoints (Ed25519) and WORM
- The worker signs `{tenantId, seq, hash, sessionHeadsDigest, prevCheckpointId, signedAt}` per tenant every `AUDIT_CHECKPOINT_INTERVAL_SECONDS` when the chain moved. It **re-verifies** everything since the previous checkpoint (and that the checkpointed row still has its signed hash) before signing; on a break it records `audit.chain.integrityViolation` and refuses to sign. Public keys (JWKS, rotation-aware) are served at `/v1/audit-checkpoints/keys` for offline verification.
- Archive: for each closed month and tenant, NDJSON.gz → S3 `PUT` with Object Lock (COMPLIANCE by default, retain-until = partition end + tenant retention, Content-MD5, `If-None-Match: *`), then GET back and compare SHA-256 + lock mode; registry rows `uploaded` → `verified`. Minimal SigV4 client (no SDK dependency).

### Partitions and retention
- Monthly RANGE partitions on `recorded_at` for `audit_events` and `session_events` (+ default partitions as a safety net), created ahead by `audit_ensure_partitions` (SECURITY DEFINER, worker only).
- Retention is a **minimum** per tenant (`settings.audit.retentionDays`, `sessionRetentionDays`, `legalHold`; env default 10 years). A partition is dropped only when, for every tenant in it: retention elapsed, no legal hold, a verified WORM archive exists, and (audit stream) a signed **boundary checkpoint** at the tenant's last seq in it exists — so the remaining chain verifies from that checkpoint. `audit_drop_partition` re-checks the owner-only global floor (`audit_policy.min_retention_days`, default 365) and computes the tenants itself before DETACH/DROP.

### Collection
- `AuditTrailInterceptor` (inside the request tx): a generic `api.<resource>.<verb>` event for any successful mutation that wrote no domain audit; `@AuditRead` for sensitive reads. `AuditFailureInterceptor` (outermost): failed/denied mutations and sensitive reads are recorded after the rollback in a fresh transaction. `AccessGuard` records `authz.access.denied`.
- Domain events: the worker consumes `DOMAIN` and audits every event whose request (tenant + correlationId) has no audit event — connector/system/job changes are never invisible; idempotent via `processed_events`.
- Auth events: already audited by the identity module (ADR-0012). Reads: PII (identity), secret metadata (integrations), audit list/export/verify.

### Query API
- `GET /v1/audit-events` (date, actor, action incl. `prefix.*`, resource, outcome, correlationId, interactionId, `q` websearch FTS; keyset by seq), `GET /v1/audit-events/export?format=csv|json` (streams in batches up to a snapshot seq; audited before the first byte; CSV formula-injection safe), `POST /v1/audit-events/verify` (range; anchor = genesis / preceding event / signed checkpoint; reports every break kind with seq), `GET /v1/audit-checkpoints[/keys]`. Actor PII is masked unless the caller may `reveal` it.

### SIEM
- `siem_destinations` (syslog RFC 5424 over TLS ≥ 1.2 with RFC 5425 framing and verified certificates; CEF or JSON payloads; HMAC-SHA256-signed webhooks with timestamp + delivery id; optional Kafka via an injected producer, acks=all, keyed by tenant). Secrets only as `secret://` references.
- Delivery: per-destination cursor, claim with lease (`FOR UPDATE SKIP LOCKED`), ordered at-least-once, never skips; exponential backoff with jitter; failure/recovery transitions audited. Receivers dedupe on `(tenantId, seq)`.

### Session events
- Separate stream `session_events` (who, which page, what was entered — masked by classification): hash chain per session, partitioned, append-only; open sessions are covered by each checkpoint's `sessionHeadsDigest`; `seal()` anchors the final head in the tenant audit chain (`runtime.session.sealed`).

### Worker
- `src/audit-worker.ts` (`pnpm --filter @verbis/api start:audit-worker`): separate process and DB role `verbis_audit_worker` (read across tenants via a SELECT-only policy; every write in a tenant transaction), jobs with no overlap and advisory/row locks so replicas are safe, LISTEN/NOTIFY wake-up for SIEM.

## Consequences
- Breaking: `audit_events`/`session_events` were recreated (migration `20261001060000_audit_v2`, v1 rows copied with `hash_version = 1`; `audit_events_v1` kept read-only for one release). The API DTO adds `resource`, keeps `target` as a deprecated alias.
- Uniqueness of `(tenant_id, seq)` is guaranteed by the head lock, not by a global index (partitioning requires the partition key); duplicates are detected by verification.
- Prisma cannot model partitions/tsvector; the drift test ignores those reviewed objects explicitly.
- Kafka client, KMS-held signing key, Secret-service resolver and compose/Helm wiring of the worker are follow-ups.
