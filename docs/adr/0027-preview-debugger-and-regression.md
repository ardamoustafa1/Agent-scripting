# ADR-0027 — Isolated runtime debugger and publication regression

Date: 2026-10-02 · Status: accepted

The designer uses `@verbis/core-runtime` for interactive previews and server-side regression. Preview commands are simulation ports; outcome/disposition/transfer/write-back never reach a platform. A sandboxed same-origin blank iframe supplies the actual device viewport, separate theme, language and UI portal surface. No runtime session is opened from query parameters.

The action executor exposes path and action-type breakpoints; page entry is a separate checkpoint. Events include safe identifiers, timestamps and durations. Browser-only checkpoints capture immutable variables, classifications, data source state, flow frames and navigation history. The timeline holds at most 1,000 events and 100 checkpoints. Returning cancels the old runtime and restores into a fresh simulation. Pending action continuations, I/O and timers are deliberately not replayed. A restored branch must restart before recording a regression scenario. These limits avoid pretending that a partly completed parallel operation can be resumed exactly.

The optional `testScenarios` field is an additive authoring extension to schema 1.1; documents without it keep their current semantics. Fixtures contain synthetic input context, mock outputs, UI events/variable edits/read acknowledgements and expected page/end/outcome/variable assertions. Twenty scenarios, 500 input steps each and existing 2 MiB document limits bound persistence. Classified PII/PCI variable recordings and assertions are rejected by shared semantic validation, including draft save and package import. Live preview results, snapshots, secret values and telemetry payloads are never written into scenarios or browser storage. The author explicitly confirms synthetic context/mock data.

A new authenticated POST authoring endpoint executes only a data source declared in the saved script, at its exact version pin, with an explicit **test** environment profile. It checks script scope and Integration execute permission on the server, uses tenant origin/SSRF/vault protections, scrubs credentials, disables response replay and audits the call. There is no production fallback. It is an authoring operation, distinct from secure agent launch.

The API reruns all saved scenarios using the same runtime and built-in component registry before approving or publishing a locked version. Results are checksum-bound and contain assertion paths and pass/fail status, not actual fixture or response values. The check and lifecycle transition share the tenant transaction. The approval UI can request the report, but a client report is never proof of success. Suites have a 10-second deadline; each case has a maximum 2-second timeout. External effects are always mocked. Timer actions are recorded and replayed as input rather than depending on wall-clock scheduling. Unsupported plugin registry pins fail closed.

Tests are added for stepping/cancellation, restore, fixture assertions/privacy, tenant/permission/profile boundaries and HTTP approval gating, plus Playwright keyboard/theme/axe scenarios. Per the user's instruction, these tests have not been executed.
